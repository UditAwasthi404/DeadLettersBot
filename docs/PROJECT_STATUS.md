## Remaining work by phase

### Phase 1

The model-tool loop is implemented in the box-host runner with bounded step budget, cancellation polling, checkpointing, and `SendToUser(end_turn)` handling. Per-account Docker bridge networks isolate VM containers from other accounts, and per-bot Xvfb/Chromium instances are created on demand with a stable bot-ID mapping, dedicated display/CDP port, and persistent browser profile. VM commands run through a process-group wrapper; explicit turn interrupts terminate shell/file commands and close the active per-bot browser connection. Docker runtime acceptance is still open. The loopback execution daemon, caller-disconnect browser cancellation/window routing, measured latency goals, and a verified full Compose deployment remain open.

### Phase 2

Initial automatic memory extraction is implemented as bounded, scope-checked append-only writes after a visible reply. A unique job is committed atomically with turn settlement; a leased background worker retries failures with capped backoff and can recover expired jobs after restart. Supporting source turns are now stored idempotently per memory fact and exposed through an account- and bot-scoped API and desktop evidence view. Opt-in background synthesis now uses a durable queue, requires repeated evidence, excludes user-authored facts, performs a separate verification call, and applies merges with optimistic concurrency and retries; runtime/model-quality acceptance and user review semantics remain open. Synchronous conversation compaction now triggers at 80% of configurable `MODEL_CONTEXT_TOKENS`, archives full source history, and selects xAI, Anthropic, OpenAI, or generic summary request/carrier formats while keeping recent exchanges and restoring the original transcript if settlement fails; long-context recovery and 50-turn acceptance remain unverified. Secure VM handoff pauses the turn, checkpoints the handoff, and resumes when the desktop sends `returnToBot`. Approved `RequestLocalExec` commands run on the connected desktop. The desktop is the only local machine; a host that is not connected returns a timeout. Subagents reuse an already queued/running worker for the same normalized task, tool set, and step budget; stall detection now marks stale tasks and requests cancellation, while restart/race acceptance, token accounting verification, and provider acceptance remain open. Peer messaging remains asynchronous.

### Phase 3

Browser recording can draft a skill from at most 10 minutes of CDP events, and the desktop can review and save that draft. A confirmed skill test queues one real routine turn. File-change routines watch a `/home/agent` path with `inotifywait`, debounce for one second, and record a history row. Gmail and Google Calendar connector-event polling is implemented with first-poll baselining, bounded ID cursors, matching routine filters, and fair rotation through 20 triggers per minute; provider/runtime acceptance remains open. Skills can now be copied to another bot with an account-scoped API; each copy has independent steps and a transactional initial version snapshot, exposed in the desktop skills panel and SDK. Cross-bot routine reassignment is implemented with account/skill ownership checks; runtime acceptance remains. Skill step errors support `stop`, bounded configurable retry, `skip`, `notify_user`, and bounded custom recovery prompts; the failure count is persisted in turn checkpoints. Retry counts are configurable from 1–10 failed actions per step (default 3), and policy/limit editing is available in the desktop; custom recovery prompts are now supported with the same attempt bound; runtime acceptance verification remains. Routine-attached skills expose `CompleteSkillStep`, allow multiple tool calls within an instruction, and enforce annotated approval checkpoints. In-turn checkpoints restore transcript context and skill progress; in-flight tool actions may repeat if a worker exits before checkpointing their results, and runtime acceptance verification remains. Routines support cron, secret-protected webhooks, inter-bot messages, and file-change watches. Inter-bot message triggers queue routine turns with an optional sender filter and hop-count propagation. Hosted startup shadow reconciliation and explicit account sync are implemented; runtime acceptance remains. Gmail, Google Calendar, Google Drive, OneDrive, Outlook Mail, Outlook Calendar, Teams, SharePoint, and Salesforce actions are implemented. Microsoft services share one OAuth connection. Live provider consent and API acceptance remain. Drive OAuth/API/UI acceptance remains. Connector disconnect now attempts provider revocation, deletes local credentials transactionally with an audit record, and reports remote revocation failures; connector OAuth uses backend tokens, so service-cookie cleanup for VM browser profiles does not apply. MCP currently supports HTTP JSON-RPC with bounded requests; multi-server prompts now direct server selection and disallow unrequested cross-server data movement. Persistent MCP health checks refresh status and discovered tools every 60 seconds with bounded concurrency; errors are now persisted as generic guidance and shown in the desktop, including for configured HTTPS tunnel URLs. AgentOS does not manage external tunnel processes. MCP strict metadata blocking is available with `MCP_STRICT_MODE=1`; endpoint DNS pinning is implemented in source, while VM-level egress policy and adversarial runtime checks remain. The desktop MCP management panel now supports server add/remove and health/tool summaries.
