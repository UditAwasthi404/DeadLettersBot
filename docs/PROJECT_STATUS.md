# Project Status

Updated 2026-10-29. The repository contains substantial Phase 1–4 foundations, but it is not yet a complete or launch-ready implementation. The detailed task list remains in [BUILD_PLAN.md](BUILD_PLAN.md).

## Implemented

- Monorepo packages for the gateway, agent runtime, inference providers, tools, memory, routines, connectors, desktop, SDK, VM manager, and shared persistence.
- PostgreSQL/Redis-backed turns, checkpoints, audit records, memories, skills, routines, Google connector accounts, API keys, and MCP server configurations.
- WebSocket chat, basic file/shell/browser/web tools, multi-bot peer messages, approval decisions, memory tools, OAuth-backed Gmail/Calendar calls, HTTP MCP discovery/calls, and an initial bounded subagent runtime with durable parent wake turns.
- Desktop chat shell with bot roster, interrupt/approval controls, memory view/edit/delete/export, simple skill and routine management, and Google connector controls.
- Docker Compose development stack, setup and backup scripts, request/turn/tool metrics, CI lint/typecheck/build workflow, and Dependabot configuration.

## Remaining work by phase

### Phase 1

The model-tool loop is implemented in the box-host runner with bounded step budget, cancellation polling, checkpointing, and `SendToUser(end_turn)` handling. Per-account Docker bridge networks isolate VM containers from other accounts, and per-bot Xvfb/Chromium instances are created on demand with a stable bot-ID mapping, dedicated display/CDP port, and persistent browser profile. VM commands run through a process-group wrapper; explicit turn interrupts terminate shell/file commands and close the active per-bot browser connection. Docker runtime acceptance is still open. The loopback execution daemon, caller-disconnect browser cancellation/window routing, measured latency goals, and a verified full Compose deployment remain open.

### Phase 2

Initial automatic memory extraction is implemented as bounded, scope-checked append-only writes after a visible reply. A unique job is committed atomically with turn settlement; a leased background worker retries failures with capped backoff and can recover expired jobs after restart. Supporting source turns are now stored idempotently per memory fact and exposed through an account- and bot-scoped API and desktop evidence view. Opt-in background synthesis now uses a durable queue, requires repeated evidence, excludes user-authored facts, performs a separate verification call, and applies merges with optimistic concurrency and retries; runtime/model-quality acceptance and user review semantics remain open. Generic synchronous conversation compaction now triggers at 80% of configurable `MODEL_CONTEXT_TOKENS`, archives full source history, summarizes older exchanges through the summarization provider, keeps recent exchanges, and restores the original transcript if settlement fails; long-context recovery and 50-turn acceptance remain unverified. Secure VM handoff and local PC execution remain open. Subagents reuse an already queued/running worker for the same normalized task, tool set, and step budget; stall detection, steering, richer task policies, token accounting verification, and runtime acceptance checks remain. Peer messaging remains asynchronous.

### Phase 3

Skill recording remains open. Skills can now be copied to another bot with an account-scoped API; each copy has independent steps and a transactional initial version snapshot, exposed in the desktop skills panel and SDK. Cross-bot routine reassignment is implemented with account/skill ownership checks; runtime acceptance remains. Skill step errors support `stop`, bounded configurable retry, `skip`, `notify_user`, and bounded custom recovery prompts; the failure count is persisted in turn checkpoints. Retry counts are configurable from 1–10 failed actions per step (default 3), and policy/limit editing is available in the desktop; custom recovery prompts are now supported with the same attempt bound; runtime acceptance verification remains. Routine-attached skills expose `CompleteSkillStep`, allow multiple tool calls within an instruction, and enforce annotated approval checkpoints. In-turn checkpoints restore transcript context and skill progress; in-flight tool actions may repeat if a worker exits before checkpointing their results, and runtime acceptance verification remains. Routines support cron and secret-protected webhooks. Inter-bot message triggers queue routine turns with an optional sender filter and hop-count propagation; connector/file event triggers, desktop setup controls, and hosted schedule reconciliation remain. Gmail, Google Calendar, and initial Google Drive actions are supported; Microsoft services and Salesforce are not. Drive OAuth/API/UI acceptance remains. Connector disconnect now attempts provider revocation, deletes local credentials transactionally with an audit record, and reports remote revocation failures; service-cookie cleanup for VM browser profiles remains unimplemented because connector OAuth is backend-token based. MCP currently supports HTTP JSON-RPC with bounded requests; multi-server prompts now direct server selection and disallow unrequested cross-server data movement. Persistent MCP health checks now refresh last-known status every 60 seconds with bounded concurrency; tunnel health is missing. MCP strict metadata blocking is available with `MCP_STRICT_MODE=1`; DNS-pinned egress and adversarial runtime checks remain. The desktop MCP management panel now supports server add/remove and health/tool summaries.

### Phase 4

The desktop still lacks attachments, Secure Handoff, VM screen streaming, local execution, and auto-update. Skills UI now edits versioned multi-step skills, approval checkpoints, and error policies; routine and connector views provide their current management controls. Skill recording remains open. Routine UI now supports cron and webhook creation, one-time secret setup, trigger/name/bot/skill editing, next-run display with the server timezone, and immediate-run confirmation; the MCP panel supports server add/remove, masked API-key entry, discovered-tool counts, and last-known health; runtime acceptance remains; manual test runs now require confirmation because configured tools may have external side effects. The SDK now has typed calls across the main account, bot, memory, skill, routine, audit, key, webhook, connector, MCP, and subagent APIs; the OpenAPI route list now covers registered HTTP routes, but typed schemas, generated SDK types, and endpoint acceptance remain. Outbound signed webhooks use a durable queue with bounded exponential retries, account-scoped history, manual retry, and configurable pruning of terminal rows; runtime acceptance remains. Compose now has optional Caddy TLS and Prometheus/Grafana profiles and binds service ports to loopback, but Compose configuration could not be validated in this environment because Docker is unavailable. The host now validates required runtime settings, endpoint/secret formats, production placeholders, provider names, feature flags, and numeric limits before connecting to services. Four dashboards are provisioned; VM container health gauges remain missing. External tool output now receives explicit untrusted-data envelopes and web extraction avoids raw HTML, but regex-based HTML reduction, adversarial runtime checks, and full source review remain open. JWT key overlap, account-wide JWT revocation, and account-scoped connector/MCP/webhook secret re-encryption are implemented but need runtime acceptance; MCP DNS pinning and the broader audit remain open. See [SECURITY_AUDIT.md](SECURITY_AUDIT.md) and [PEN_TEST_CHECKLIST.md](PEN_TEST_CHECKLIST.md). An initial Helm chart provisions the host, PostgreSQL, Redis, MinIO, persistent volumes, Secrets, and optional Ingress, but it does not support VM automation, HPA, cert-manager, or Kubernetes runtime acceptance. Initial sizing estimates and a forward-migration/restore guide are documented in [RESOURCE_SIZING.md](RESOURCE_SIZING.md) and [UPGRADING.md](UPGRADING.md); empirical capacity data and a zero-downtime upgrade procedure remain open. VM garbage collection, OpenTelemetry tracing, runtime metrics scrape validation, full security review, network egress policy, load/evaluation suites, and release automation/publication are still required.

## Verification and operational prerequisites

As of 2026-10-29, `pnpm lint`, `pnpm typecheck`, and `pnpm build` pass after the durable memory job, memory evidence, opt-in synthesis queue and worker, skill error-policy, copy-on-assign, startup configuration validation, initial Helm chart, OpenAPI route coverage, JWT sessions, connector-secret rotation, external-output trust boundary, synchronous compaction, duplicate-subagent reuse, Google Drive connector wiring, routine webhook setup/editing/next-run changes, audited connector disconnect behavior, desktop MCP server management, opt-in MCP strict metadata blocking, periodic MCP health checks, the versioned skill editor, and bounded skill recovery prompts. `MCP_STRICT_MODE` is wired through `.env.example`, Compose, Helm values, and self-hosting docs. `MODEL_CONTEXT_TOKENS` and `MEMORY_SYNTHESIS_ENABLED` are validated and exposed in `.env.example`, Compose, Helm values, and self-hosting docs. The Drizzle migration journal now includes the synthesis-job table. `FetchURL` caps response reads at 2 MiB and returned text at 8,000 characters. Automated tests were not run. Compose configuration, shell image scripts, VM runtime behavior, JWT/connector-key rotation and revocation behavior, compaction and synthesis quality/recovery, Google Drive OAuth/permissions, adversarial injection resistance, and Helm rendering could not be validated because Docker, Helm, a usable Bash runtime, and a YAML parser are unavailable in this environment. A working self-hosted instance still requires Docker, a configured inference provider for live model calls, and Google OAuth credentials for Google connectors. Desktop installers, Docker Hub images, and npm publication have not been released.
